# Financial documents and email jobs

`src/documents.ts` exports `documentRoutes`, mounted on the authenticated organization business router. Reads, PDFs and delivery history require `finance:read`; manual sends require `payment:write`. All resource lookups and worker document generation include the organization. Email and payment provider secrets belong only on the server.

Private mutations also reject foreign or opaque browser origins; the browser's origin must exactly match `FRONTEND_URL`. Origin-less CLI requests remain supported. `GET /payments/:id/receipt.pdf` requires an explicit `X-Organization-Id` header, already supplied by the React client, because first issuance of a historical receipt makes that payment immutable. The normal membership check still validates that workspace. Public payment callbacks are outside this private origin gate.

| Method | Path | Input |
| --- | --- | --- |
| GET | `/billing/invoices/:id/pdf` | Invoice PDF |
| GET | `/payments/:id/receipt.pdf` | Settled payment receipt PDF |
| GET | `/reports/financial.pdf` | `?type=collections\|arrears&month=YYYY-MM` |
| POST | `/billing/invoices/:id/send` | `{ "email": "optional-override@example.com" }` or `{}` |
| POST | `/payments/:id/send-receipt` | Same optional email override |
| POST | `/reports/send` | `{ "type": "collections", "month": "2026-11", "email": "recipient@example.com" }` |
| GET | `/billing/deliveries` | Latest 50 delivery outcomes for the active organization |

Manual sends require a valid configured sender and recipient before creating a job. Missing email configuration returns HTTP 503. The response contains `data` with `id`, `kind`, `status`, `recipient`, `attempts`, `availableAt`, `sentAt`, `lastError`, `createdAt`, `invoiceId`, and `paymentId`. HTTP 200 plus `SENT` means Brevo accepted the email, not that it reached an inbox. HTTP 202 plus `QUEUED`/`SENDING` means work is pending; final `FAILED` returns HTTP 503. A skipped job has status `SKIPPED`. No response describes an unconfigured sender as successful.

PDFs are generated by PDFKit without HTML rendering, remote assets or browser credentials. DejaVu fonts and their license are bundled in `assets/fonts` and must remain with the compiled deployment. Invoice names and rent use issue-time snapshots. Receipts distinguish historical, manual and provider-verified mobile-money records; generating an old receipt first assigns its stable receipt number and name snapshots inside a locked transaction. That prevents later editing of a payment after its receipt has been issued. A voided payment can be downloaded as a visibly VOID document, but it is not emailed as a new confirmation. Collection reports exclude voided payments. Arrears reports show **current balances of invoices due through the selected month**; they do not claim to reconstruct historical balances before later allocations.

## Brevo configuration

Set these server environment variables only after the sender has been verified in Brevo:

```text
BREVO_API_KEY=<transactional API key>
EMAIL_FROM=<verified sender email>
FRONTEND_URL=https://remote-property-management.onrender.com
```

The email transport uses HTTPS `POST https://api.brevo.com/v3/smtp/email`, `api-key`, `htmlContent`, and base64 PDF attachments. `FRONTEND_URL` supplies the optional Open REMOTE login link; malformed URLs are omitted. Nothing is sent when a module is imported. Provider configuration and sender approval are operator prerequisites; this change does not create a Brevo account or send a real test email.

Official references: [transactional email API](https://developers.brevo.com/reference/send-transac-email) for attachments and the message `headers` object; [Brevo idempotency announcement](https://developers.brevo.com/changelog/2021/11/10) for `idempotencyKey`. Each durable job UUID is reused as the transactional message's idempotency key. Brevo's documented duplicate-idempotency error is treated as a previously accepted job only when its error message explicitly identifies idempotency.

## Running the worker

Build the server and run `npm run jobs` (`node dist/jobs/run.js`). An operator may schedule this command every five minutes in the deployment environment, with the same server environment and database as the API. No cron service is created by this implementation. The command exits after one scheduling and dispatch pass. It logs aggregate counts, not tenant addresses or API keys, and exits nonzero if a scheduling organization fails.

Exports from `src/jobs/index.ts`:

- `runJobsOnce(now?)` schedules and attempts up to 25 due deliveries.
- `scheduleBillingAndReminders(now?)` generates only the current Kampala month for organizations with monthly billing enabled. It queues reminders only for opted-in organizations, at/after 09:00 Kampala, on the due day and every seventh overdue day. Repeated runs deduplicate by organization/invoice/calendar day. Missing contact emails are recorded as SKIPPED.
- `processDeliveryQueue(limit?, now?)` processes due or abandoned deliveries.
- `runDeliveryJob(id, organizationId?, now?)` attempts one job. Pass an organization ID for request-driven dispatch.
- `queueDocumentDelivery(input)` inserts/upserts a durable job. Billing transactions queue receipt jobs directly under the stable key `receipt:<paymentId>` so duplicate payment callbacks do not create additional confirmations.

Jobs persist as QUEUED/SENDING/SENT/FAILED/SKIPPED. Claiming uses an atomic conditional update with a two-minute lease, and a completion may update only its own claim. No database transaction spans the provider HTTP request. Attempts are bounded to four with one-, two- and four-minute backoff; each actual request times out after ten seconds. Reminders recheck the organization opt-in, recipient contact, scheduled day and unpaid balance at delivery. Old reminder days are skipped instead of sending a backlog when email is enabled later. Payments that have been voided are not confirmed. Paid/void/missing targets are skipped. If sender configuration is absent, automatic jobs remain queued without consuming an attempt.

Delivery is not exactly once across every possible crash: the provider's idempotency guarantee has a finite lifetime. This implementation conservatively stops uncertain retries after 15 minutes from the first claim and marks the job FAILED for operator review. A five-minute cron cadence can therefore reach the time boundary before all four attempts. Review the Brevo history before deliberately issuing another manual send after an uncertain failure. A repeated manual action within the same minute shares a job; a later deliberate resend creates a new job and can send another copy.

Automatic billing and reminders default off. Opt in per organization in Settings only after the rent schedule and tenant contacts are correct. Configuration-gated transport has no live sender verification in this repository; tests must mock the HTTPS provider and use an isolated test database.
